# gvsoc_rvvi — GVSOC bridge for CV32E40P UVM co-simulation

Bridge library connecting GVSOC (the PULP/GAP virtual-platform simulator) to the RVVI
interface used by the core-v-verif UVM testbench, enabling instruction-accurate
step-and-compare co-simulation of CV32E40P.

The bridge follows GVSOC's official pattern for control from an external
simulator (tutorial `17_how_to_control_gvsoc_from_an_external_simulator` in
the GVSOC developer manual), driving the engine through the `gv::Gvsoc` API
(`gvsoc/engine/engine/include/gv/gvsoc.hpp`: `gvsoc_new` +
`GvsocConf.config_path` + `open`/`step`).

## Repository layout

```
gvsoc_rvvi/
├── gvsoc/            ← GVSOC simulator (git submodule → FondazioneChipsIT/gvsoc)
├── RVVI/             ← RVVI standard API, host headers (git submodule → riscv-verification/RVVI)
├── rvvi_trace2api.sv ← SV DPI driver: reads the rvviTrace interface and drives the RVVI API (RVVI-TRACE → RVVI-API)
├── rvvi_api2gvsoc.cpp   ← C++ DPI bridge: implements the RVVI API on top of the GVSOC engine (RVVI-API → GVSOC)
├── gvsoc_engine_v2.cpp ← engine wrapper: iss_v2 core, commit-stream retires,
│                        wire-driven IRQ injection
├── gvsoc_engine.hpp  ← pure-C engine API (incl. the capability queries)
├── rvvi_text_writer.cpp/.hpp ← canonical RVVI-TEXT trace formatter (shared by bridge and shim)
├── rvvi_text_dpi.cpp/.hpp    ← DPI shim around the formatter for RTL-only tracing
├── test/             ← deterministic formatter unit test (make test)
├── docs/             ← architecture guides + RVVI-TEXT tracing guide
├── Makefile          ← build targets (see below)
└── .gitmodules       ← gvsoc + RVVI submodule definitions
```

The platform Python targets (`cv32e40p-v2-standalone*.py`) and the exit
device (`cv32e40p_exit_device.py/.cpp`) do not live at the top level: they
sit inside the submodule, in `gvsoc/pulp/` and
`gvsoc/pulp/pulp/cv32e40p_exit/` respectively, and are installed by
`make gvsoc`. `gvsoc_config.json` is not versioned: it is an artifact
generated by `make config-v2` (it is in `.gitignore`).

## Prerequisites

- cmake ≥ 3.16, g++ ≥ 9 (C++17)
- Questa simulator (for `-I$(QUESTA_HOME)/include` when compiling the bridge)
- The `gvsoc_env_3_12` micromamba Python environment (see below) — needed by `gvrun`
  and by config generation.

## Python environment (micromamba)

GVSOC and its tools (`gvrun`, `gvsoc_config.json` generation) run inside a dedicated
micromamba environment: `gvsoc_env_3_12` (Python 3.12). All `make gvsoc` /
`make config` / `make trace` commands must be executed inside this env.

**Using it** (already created on the development server):

```bash
# A) activate it in the current shell, then use make normally:
micromamba activate gvsoc_env_3_12
make gvsoc

# B) or run a single command without activating (the form used by
#    mk/Common.mk):
micromamba run -n gvsoc_env_3_12 make config BINARY=/path/to/test.elf
```

**Creating it from scratch** (only if missing — check with `micromamba env list`):

```bash
micromamba create -n gvsoc_env_3_12 python=3.12
micromamba run -n gvsoc_env_3_12 pip install -r gvsoc/requirements.txt
```

> Do not install packages system-wide: always use the micromamba env.

## Build steps

### 1. Initialize the submodules

```bash
git submodule update --init --recursive
```

### 2. Build GVSOC

```bash
make gvsoc
```

Builds the iss_v2 targets (`cv32e40p-v2-standalone`, `-fpu`, `-zfinx`,
`-nopulp`, and the `cv32e40p-v2-spike` variants — the core configuration is
baked into each target name): ISS models + all CV32E40P ISA models. Build
in `build/`, install in `install/`.

### 3. Generate `gvsoc_config.json`

```bash
make config-v2 BINARY=/path/to/test.elf [V2_TARGET=cv32e40p-v2-standalone-fpu]
```

`make config-v2` without `BINARY=` fails on purpose (`$(error BINARY not set)`).

Runs `gvrun prepare` and generates the JSON topology. The core
configuration is baked into the target name, so there are no `--parameter`
knobs besides the binary. In the production DPI flow this step is handled
by the `generate_gvsoc_dpi_config` recipe in `cv32e40p/sim/uvmt/Makefile`
(which invokes `make config-v2` here, generating one
`gvsoc_config_v2_<CFG>.json` template per testbench CFG); the actual ELF
path is injected at runtime by the bridge (`rvvi_api2gvsoc.cpp`) using the
real binary passed from UVM via `rvviRefInit()`. The generated file is
gitignored.

This step needs the Python env with the gvsoc dependencies —
`micromamba run -n gvsoc_env_3_12 make config-v2 BINARY=...`.

### 4. Build the bridge library/libraries

```bash
make            # same as 'make all'
```

Produces three libraries:

| Library | Role |
|---|---|
| `libgvsoc_rvvi_v2.so` | DPI bridge (iss_v2 reference core), standard variant (FP with `fregs[]`) |
| `libgvsoc_rvvi_v2_zfinx.so` | DPI bridge, ZFINX — compiled with `ISS_SINGLE_REGFILE=1` to match the ZFINX ISS regfile layout |
| `librvvi_text.so` | RVVI-TEXT writer for RTL-only tracing — no GVSOC dependency (see `docs/RVVI_TEXT_TRACING.md`) |

The two bridge libraries link `install/lib/libpulpvp.so` with an embedded rpath
(no `LD_LIBRARY_PATH` needed at runtime). The DPI test selects the correct
variant (standard/ZFINX) via the CFG in `mk/Common.mk`, which sets
`GVSOC_RVVI_MODEL`.

For C++ debugging (gdb / VS Code), `make DEBUG=1 ...` adds `-g -O0` — see
[`docs/DEBUG_COSIM.md`](docs/DEBUG_COSIM.md).

## core-v-verif integration

The parent repo invokes these targets through the `generate_gvsoc_config` /
`generate_gvsoc_dpi_config` recipes in `cv32e40p/sim/uvmt/Makefile`; `mk/Common.mk`
derives the `GVSOC_*` variables and exports `GVSOC_CONFIG`.
To enable GVSOC as the ISS in the CV32E40P UVM testbench:

```bash
# from the cv32e40p/sim/uvmt/ directory
make comp USE_ISS=YES ISS=GVSOC
make test TEST=hello-world USE_ISS=YES ISS=GVSOC COMP=NO
```

The reference model runs on the iss_v2 core: the bridge library and the
`gvsoc_config_v2_<CFG>.json` template are selected automatically per CFG.
There is no core selector — the testbench Makefile fails with an explicit
error if `GVSOC_ISS_V2=NO` is passed on the make line.

Environment variable set by `mk/Common.mk`:
- `GVSOC_CONFIG` — absolute path to the generated config
  (`gvsoc_config_v2_<CFG>.json`)

## Files required at runtime

| File | Role |
|---|---|
| `libgvsoc_rvvi_v2.so` / `libgvsoc_rvvi_v2_zfinx.so` | DPI bridge loaded by the simulator via `-sv_lib` (ZFINX variant chosen by the CFG in `mk/Common.mk`) |
| `install/lib/libpulpvp.so` | GVSOC engine (found through the embedded rpath) |
| `gvsoc_config_v2_<CFG>.json` | Generated topology (`gvrun prepare`): describes the system — models, parameters, ELF — that the engine instantiates via `gv::gvsoc_new()` |

The models in `install/models/` are loaded automatically by `libpulpvp.so`
through `dlopen`, based on the paths in `gvsoc_config.json`.

## Implementation status

- **State readback** (PC, GPR, CSR): full step-and-compare comparison. The list of compared
  CSRs (19) and the volatile masks are configured on the testbench side in `ref_init`
  (`cv32e40p/tb/uvmt/uvmt_cv32e40p_gvsoc_wrap.sv`) — that is the source of truth, not the bridge.
- **`rvviRefEventStep`**: advances GVSOC by one instruction (retire-based), not by one
  clock period, by popping one commit from the iss_v2 commit stream.
- **Interrupt injection** — the bridge implements two mechanisms:
  1. Reactive (default): `rvviRefNetSet` → `gvsoc_engine_set_irq` drives one of the
     19 wires of the `cv32e40p_irq_injector` component (bound via `wire_bind` at
     init); `mip` is updated by the ISS interrupt model itself and the ISS takes
     the IRQ in its natural loop.
  2. Informed-injection / OVPSim deferint (opt-in via the `+rvvi_informed_irq` plusarg,
     default off): the bridge detects the vectored entry
     (DUT-PC == `mtvec` base + cause·4) and calls
     `gvsoc_engine_take_irq_for_one_step()`, letting the ISS compute the handler
     entry from `mcause`.

## Known limitations

- **IRQ timing (reactive path)**: GVSOC evaluates interrupts post-execute, the RTL does so
  combinationally in the DECODE FSM, so the entry is desynchronized by about a cycle.
  Informed-injection (above) is the mechanism to align the entry when strict parity
  is needed.
- **Debug mode**: the bridge follows the DUT into debug mode through the informed
  entry path (on the `rvvi.debug_mode` 0→1 edge the ISS performs the entry itself).
  The residual is a one-instruction retire misalignment inside the debug ROM when
  debug entries re-arm in rapid succession — the two debug×hwloop KNOWN_FAIL lanes
  in `test/quick_val.sh`.

For the current validation status refer to the latest `test/quick_val.sh`
run in the parent repo, not to this README.
