# gvsoc_rvvi — GVSOC bridge for CV32E40P UVM co-simulation

Bridge library connecting GVSOC (the PULP/GAP virtual-platform simulator) to the RVVI
interface used by the core-v-verif UVM testbench, enabling instruction-accurate
step-and-compare co-simulation of CV32E40P.

> This bridge implements the official GVSOC pattern of **control from an external simulator**
> (tutorial `gvsoc/core/docs/developer_manual/tutorials/17_how_to_control_gvsoc_from_an_external_simulator/`).
> API: `gvsoc/engine/engine/include/gv/gvsoc.hpp` — `gvsoc_new` + `GvsocConf.config_path` + `open`/`step`.
> Full architectural detail (engine, bridge, RVVI conformance, fragilities, future levers): [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).
> Deep dive on the GVSOC system itself (`gvsoc.hpp` API, TimeEngine, ISS hookup, gdbserver, GVSOC-side improvements): [`docs/GVSOC_ENGINE.md`](docs/GVSOC_ENGINE.md).

## Repository layout

```
gvsoc_rvvi/
├── gvsoc/            ← GVSOC simulator (git submodule → FondazioneChipsIT/gvsoc)
├── RVVI/             ← RVVI standard API, host headers (git submodule → riscv-verification/RVVI)
├── rvvi_trace2api.sv ← SV DPI driver: reads the rvviTrace interface and drives the RVVI API (RVVI-TRACE → RVVI-API)
├── rvvi_api2gvsoc.cpp   ← C++ DPI bridge: implements the RVVI API on top of the GVSOC engine (RVVI-API → GVSOC)
├── gvsoc_engine.cpp  ← embedded GVSOC engine: ISS instance, retire-based stepping,
├── gvsoc_engine.hpp  ←   PC/GPR/CSR/mip access, IRQ and debug injection
├── Makefile          ← build targets (see below)
└── .gitmodules       ← gvsoc + RVVI submodule definitions
```

> **Note.** The platform Python target (`cv32e40p-standalone.py`) and the exit device
> (`cv32e40p_exit_device.py/.cpp`) do **not** live at the top level: they sit inside the
> submodule, in `gvsoc/pulp/` and `gvsoc/pulp/pulp/cv32e40p_exit/` respectively, and are
> installed by `make gvsoc`.
> `gvsoc_config.json` is **not versioned**: it is an artifact generated by `make config`
> (it is in `.gitignore`).

## Prerequisites

- cmake ≥ 3.16, g++ ≥ 9 (C++17)
- Questa simulator (for `-I$(QUESTA_HOME)/include` when compiling the bridge)
- The `gvsoc_env_3_12` micromamba Python environment (see below) — needed by `gvrun`
  and by config generation.

## Python environment (micromamba)

GVSOC and its tools (`gvrun`, `gvsoc_config.json` generation) run inside a dedicated
micromamba environment: **`gvsoc_env_3_12`** (Python 3.12). All `make gvsoc` /
`make config` / `make trace` commands must be executed inside this env.

**Using it** (already created on the development server):

```bash
# A) activate it in the current shell, then use make normally:
micromamba activate gvsoc_env_3_12
make gvsoc

# B) or run a single command without activating (the form used by
#    mk/Common.mk):
micromamba run -n gvsoc_env_3_12 make config BINARY=/path/to/test.elf
```

**Creating it from scratch** (only if missing — check with `micromamba env list`):

```bash
micromamba create -n gvsoc_env_3_12 python=3.12
micromamba run -n gvsoc_env_3_12 pip install -r gvsoc/requirements.txt
```

> Do not install packages system-wide: always use the micromamba env.

## Build steps

### 1. Initialize the submodules

```bash
git submodule update --init --recursive
```

### 2. Build GVSOC

```bash
make gvsoc
```

Builds the `cv32e40p-standalone` target in **6 variants** (base, `corev_pulp`, `fpu`,
`fpu`+`zfinx`, `corev_pulp`+`fpu`, `corev_pulp`+`fpu`+`zfinx`): ISS model (`Cv32e40pCsr`) +
all CV32E40P ISA models. Build in `build/`, install in `install/`.

### 3. Generate `gvsoc_config.json`

```bash
make config BINARY=/path/to/test.elf [COREV_PULP=True] [FPU=True] [ZFINX=True]
```

> `make config` **without `BINARY=` fails on purpose** (`$(error BINARY not set)`).

Runs `gvrun prepare` and generates the JSON topology. In the production DPI flow this step
is handled by the `generate_gvsoc_dpi_config` recipe in `cv32e40p/sim/uvmt/Makefile` (which
invokes `make config` here); the actual ELF path is **injected at runtime by the bridge**
(`rvvi_api2gvsoc.cpp`) using the real binary passed from UVM via `rvviRefInit()`. The
generated file is gitignored.

> **Server:** requires the Python env with the gvsoc dependencies —
> `micromamba run -n gvsoc_env_3_12 make config BINARY=...`.

### 4. Build the bridge library/libraries

```bash
make            # same as 'make all'
```

Produces **two** libraries:

| Library | Variant |
|---|---|
| `libgvsoc_rvvi.so` | standard (FP with `fregs[]`) |
| `libgvsoc_rvvi_zfinx.so` | ZFINX — compiled with `ISS_SINGLE_REGFILE=1` to match the ZFINX ISS regfile layout |

Both link `install/lib/libpulpvp.so` with an embedded rpath (no `LD_LIBRARY_PATH`
needed at runtime). The DPI test selects the correct variant via `GVSOC_RVVI_MODEL`
in `mk/Common.mk`.

> For C++ debugging (gdb / VS Code): `make DEBUG=1 ...` adds `-g -O0`.

## core-v-verif integration

The parent repo invokes these targets through the `generate_gvsoc_config` /
`generate_gvsoc_dpi_config` recipes in `cv32e40p/sim/uvmt/Makefile`; `mk/Common.mk`
derives the `GVSOC_*` variables and exports `GVSOC_CONFIG`.
To enable GVSOC as the ISS in the CV32E40P UVM testbench:

```bash
# from the cv32e40p/sim/uvmt/ directory
make comp USE_ISS=YES ISS=GVSOC
make test TEST=hello-world USE_ISS=YES ISS=GVSOC COMP=NO
```

Environment variable set by `mk/Common.mk`:
- `GVSOC_CONFIG` — absolute path to `gvsoc_config.json`

## Files required at runtime

| File | Role |
|---|---|
| `libgvsoc_rvvi.so` / `libgvsoc_rvvi_zfinx.so` | DPI bridge loaded by the simulator via `-sv_lib` (variant chosen by `mk/Common.mk`) |
| `install/lib/libpulpvp.so` | GVSOC engine (found through the embedded rpath) |
| `gvsoc_config.json` | Generated topology (`gvrun prepare`): describes the system — models, parameters, ELF — that the engine instantiates via `gv::gvsoc_new()` |

The models in `install/models/` are loaded automatically by `libpulpvp.so`
through `dlopen`, based on the paths in `gvsoc_config.json`.

## Implementation status (updated 2026-06-22)

- **State readback** (PC, GPR, CSR): full step-and-compare comparison. The list of compared
  CSRs (**19**) and the volatile masks are configured **on the testbench side** in `ref_init`
  (`cv32e40p/tb/uvmt/uvmt_cv32e40p_gvsoc_wrap.sv`) — that is the source of truth, not the bridge.
- **`rvviRefEventStep`**: advances GVSOC by **one instruction** (retire-based), not by one
  clock period.
- **Interrupt injection** — the bridge implements two mechanisms:
  1. **Reactive (default)**: `rvviRefNetSet` → `gvsoc_engine_set_irq` → direct set of the
     `mip` CSR (`LocalInterrupt0-15` as a net group). The ISS takes the IRQ in its natural loop.
  2. **Informed-injection / OVPSim deferint** (opt-in via the `+rvvi_informed_irq` plusarg,
     **default OFF**): the bridge detects the vectored entry (DUT-PC == `mtvec` base + cause·4)
     and calls `gvsoc_engine_take_irq_for_one_step()`, letting the ISS compute the handler
     entry from `mcause`.

## Known limitations

- **IRQ timing (reactive path)**: GVSOC evaluates interrupts post-execute, the RTL does so
  combinationally in the DECODE FSM → ~1-cycle desync on entry. Informed-injection (above)
  is the mechanism to align the entry when strict parity is needed.
- **Debug mode**: `haltreq` is **partially** wired (`gvsoc_engine.cpp` sets `req_debug`
  + `dcsr.cause`), but the full side effects of `debug_req()` (WFI exit, switch to full-exec)
  are not triggered because the method is not linkable via DPI. Debug single-stepping
  remains limited.

> For the **current regression status** (which tests pass in DPI vs `GVSOC_TRACE`) refer
> to the parent repo's regression report, not to this README.
